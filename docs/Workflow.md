# Workflow

So, what does this thing actually do? We'll vaguely go through it step-by-step,
but ultimately you should just read the code if you really need to know what's
going on. (That's part of the reason for it being open source!)

## Encryption

The goal of this workflow is to take one file and securely transform it into a
set of encrypted files. This transformation is reversible, but only under certain
conditions.

 1. Command-line arguments are parsed and validated.
 2. A new primary key and nonce are generated.
 3. The plaintext from the input file is read and encrypted.
 4. For each canary, a canary key and nonce are created.
 5. Each canary key and nonce are used to encrypt the primary key.
 6. The ciphertext is split into _t_ parts (where _t_ is the number of
    trustees). Each trustee receives every part except the _q-1_ consecutive
    parts (wrapping around) that start at their own ordinal, where _q_ is the
    quorum. This means no single shard carries the whole ciphertext, but every
    part is absent from exactly _q-1_ shards, so any quorum of shards holds all
    of them between them.
 7. A shard with a shard key and nonce are created for each trustee.
 8. For each trustee, all combinations of _q-1_ other trustees are generated.
 9. For each combination, a combo key and nonce formed by XORing the corresponding
    keys and nonces of the selected trustees.
10. The encrypted primary key is sealed with the combo key and nonce. Together
    with the list of trustees in the combination, this is a "fragment", and it
    is added to the shard for the current trustee.
11. Unless codes are disabled, a recovery code is generated for each trustee,
    and the shard's secrets (its key and fragments) are sealed under a key
    derived from that code with Argon2id (64 MiB, 3 passes). The codes are
    printed once and stored nowhere. The ciphertext parts stay in the clear on
    purpose, so a shard whose code was lost still contributes them.
12. The canaries and shards are serialized independently of the payload workflow.
13. A payload is generated from the metadata and each serialized canary or shard.
14. Each payload is saved to the disk.

## Decryption

The goal of this workflow is to take a directory of files and securely reverse
the encryption workflow such that it yields a single file of plaintext.

 1. Command-line arguments are parsed and validated.
 2. Any provided recovery codes are parsed (failing fast on a typo) and
    matched to shards by their leading ordinal.
 3. The specified files are loaded, and any canaries or shards are extracted.
 4. The shards are sorted by creation order. Each locked shard whose code was
    provided is unlocked; a locked shard without its code stays shut and
    contributes only its ciphertext parts below.
 5. A fragment is chosen from the first unlocked shard whose listed trustees
    have all provided (and unlocked) their shards. (Every shard has a fragment
    for every quorum its trustee could be part of, so any shard will do.)
 6. A combo key and nonce are generated by XORing the keys and nonces of the
    trustees that fragment lists.
 7. The combo key is used to unseal the fragment, which yields the encrypted
    primary key.
 8. The ciphertext parts carried by every shard provided are gathered up; any
    part that is missing, or that two shards disagree about, aborts decryption
    (the latter means the shards came from different encryption runs).
 9. The parts are merged in order into a single ciphertext.
10. The canaries are sorted by creation in descending order.
11. Each canary is used to further decrypt the primary key.
12. The primary key is used to decrypt the ciphertext.
13. The plaintext is saved to disk.

## Considerations

- The ciphertext itself is only encrypted with one key using AES256-GCM-SIV.
- The encryption operations that occur later on only mutate the primary encryption
  key itself.
- A fragment can only be unsealed by someone holding the shard it sits on plus
  every shard its combo lists, which is a quorum. With fewer shards than that,
  every fragment is indistinguishable from random bytes, so nothing about its
  contents matters until the quorum exists.
- With recovery codes enabled, an attacker needs a quorum of shard *files* and
  a quorum of *codes*: a locked file alone yields only ciphertext parts, and a
  code alone yields nothing. Canaries are not locked -- they stay under the
  creator's own control, and there is no second party to deliver a code to.
- A single shard does reveal how many trustees there are and how many are
  needed (the fragment lists and the ciphertext partition give both away), and
  the description is stored in the clear. Assume anyone who finds a shard
  knows that much, and don't put names in the description.
- The tool refuses trustee/quorum combinations that would need more than
  100,000 fragments per shard (each shard needs _C(t-1, q-1)_ of them). In
  practice that is a ceiling around 20 trustees with a quorum near half.
- The ciphertext is carried once per shard (minus a window of _q-1_ parts), not
  once per fragment, so shard size is roughly the size of the ciphertext no
  matter how many trustees there are. The number of _fragments_ per shard is
  still _C(t-1, q-1)_, but each is only a few dozen bytes.
- No single shard carries the whole ciphertext: every shard lacks exactly
  _(q-1)/t_ of it. Two shards that lack different windows do, between them,
  carry the whole ciphertext, so this is only a nuisance to someone who has
  broken AES and holds exactly one shard; it is not what keeps the plaintext
  secret. The primary key is.
- Canaries are all required, which means that while there's redundancy built into
  the system for trustees and their shards, the loss of a canary makes the
  encryption workflow irreversible. But, you can put the same canary in more than
  one place or tarball a `ddwill` result and run it through again.
